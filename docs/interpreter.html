Strada Interpreter

A bytecode VM that compiles Strada's AST to bytecode and executes it via a computed goto dispatch loop. 4-5x faster than Perl 5.38.

Opt-in build: strada-interp is no longer built by default — run make interpreter in the repo to build it. The everyday strada --repl and strada --script flows now route through strada-jit (real native compilation via tcc/gcc + dlopen) so they support the full Strada language with no semantic gaps. The interpreter described on this page is useful for embedding, experimentation, and anywhere you want bytecode execution without invoking gcc. The binary is interpreter/strada-interp.
No C compiler needed at runtime The interpreter compiles Strada code to bytecode and runs it on the VM. No gcc or tcc required (except for __C__ blocks, which are JIT-compiled and cached).

Overview

Strada offers two execution paths for your code:

Compiled (stradac) VM (strada-interp)
How it works Generates C code, compiles to native binary AST → bytecode → VM dispatch
Requires C compiler Yes (gcc) No (except __C__ blocks)
Startup time Slow (compilation step) Fast (parse + bytecode compile)
Runtime speed Fastest (native code) Fast (4-5x faster than Perl 5.38)
Best for Production, performance Scripts, file execution, REPL, embedded eval

Both paths share the same Lexer and Parser front-end, so valid Strada code works with either of them.

Running Programs

# Build the interpreter
make interpreter

# Run a Strada program on the bytecode VM
./interpreter/strada-interp program.strada

# With library search paths
./interpreter/strada-interp -L lib program.strada

# Start the interactive REPL
./interpreter/strada-interp

Interactive REPL

When run without arguments, the interpreter starts an interactive REPL with readline support (line editing, history), backed by a persistent bytecode VM session:

strada> my int $x = 42;
42
strada> $x * 2
84
strada> func square(int $n) int {
...         return $n * $n;
...     }
strada> square(7)
49

Variables and function definitions persist across evaluations until .clear. Multi-line input is detected automatically when braces, parentheses, or brackets are unbalanced, inside a heredoc body, and when a line ends in a binary operator (my $t = 1 + continues on the next line). REPL commands: .help, .vars, .funcs, .load FILE, .clear, .quit.

See REPL & Scripting for REPL commands, scripting, and profiling features.

Embedded Eval

The interpreter can be embedded inside compiled Strada programs through the Eval module (lib/Eval.strada, built by make libs), which bundles the lexer, parser and Strada::Interpreter. This enables runtime code evaluation without needing a C compiler at runtime. (use Strada::Interpreter; on its own does not compile: it lacks the front-end.) The same program also runs unchanged under strada-interp.

use lib "lib";
use Eval;

# Optional: kept for compatibility (eval initializes on demand)
Strada::Interpreter::init();

# Evaluate expressions
my scalar $result = Strada::Interpreter::eval_string("1 + 2");
say($result);  # 3

# Variables persist across calls
Strada::Interpreter::eval_string("my int \$x = 10;");
my scalar $val = Strada::Interpreter::eval_string("\$x * 5");
say($val);  # 50

# Function definitions persist
Strada::Interpreter::eval_string("func twice(int \$n) int { return \$n * 2; }");
say(Strada::Interpreter::eval_string("twice(21)"));  # 42

# Reset all state
Strada::Interpreter::reset();

Eval API

Function Description
Strada::Interpreter::init() No-op kept for compatibility; the eval session initializes on demand
Strada::Interpreter::eval_string($code) Evaluate Strada code on the bytecode VM and return the result; throws on parse, compile or runtime errors
Strada::Interpreter::eval($code) Same as eval_string (also available as eval_string_vm)
Strada::Interpreter::reset() Clear all persisted state (variables, functions, enums, constants)
Strada::Interpreter::set_eval_backend($b) Legacy compatibility wrapper; the backend is always the bytecode VM

Interpreter vs JIT

Strada also provides Strada::JIT, which evaluates code by compiling to a shared library at runtime. The two approaches serve different needs:

Strada::Interpreter Strada::JIT
Execution Bytecode VM Compile to .so, dlopen, execute
Requires C compiler No Yes (gcc or tcc)
__C__ blocks JIT-compiled and cached Supported
Async/await Yes Yes
Per-eval overhead Low (parse + bytecode compile) Higher (compile + link + load)
Execution speed Fast (bytecode VM) Fastest (native code)
Best for REPL, scripting, no-compiler envs Plugin systems, perf-sensitive eval

Architecture

The interpreter reuses the compiler's Lexer and Parser front-end. The AST is compiled to bytecode and executed by a computed-goto dispatch loop. Values use a tagged-pointer representation, so integers need no heap allocation (like the compiled runtime's tagged integers).

Component Source Purpose
Lexer compiler/Lexer.strada Tokenizes source (shared with compiler)
Parser compiler/Parser.strada Builds AST (shared with compiler)
VM Compiler interpreter/vm_compiler.c Compiles AST to bytecode
Bytecode VM interpreter/vm.c Bytecode dispatch loop, with JIT compilation for __C__ blocks
Session manager lib/Strada/Interpreter.strada VM session wrapper and the eval_string / Eval API
Driver interpreter/Main.strada File execution, -e, and REPL

Scope and Semantics

Lexical variables (my) and closures compile to VM slots; our globals and local overrides live in hash-backed global tables. Control flow (next, last, redo, return) and try/catch/finally unwind frames and local stacks deterministically. The VM requires every variable to be declared with my or our.

__C__ Blocks

__C__ blocks are JIT-compiled with gcc into a shared object and loaded with dlopen. All blocks of a program go into one shared object, so file-scope static state is shared between them. Compiled objects are cached in ~/.cache/strada/cblocks/ (7-day LRU eviction), so later runs do not recompile; link_lib libraries are linked into the JIT object.

Supported Features

The interpreter supports the full Strada language:

  • Types: int, num, str, scalar, array, hash, undef
  • Variables: my, our, local, const, enum
  • Operators: arithmetic, string (., x), comparison, logical, assignment, ternary
  • Control flow: if/elsif/else, unless, while, until, for, foreach, do-while, loop labels, statement modifiers
  • Functions: func/fn, closures, variadic (...@args), spread operator
  • OOP: packages, extends, has ro|rw, before/after/around, isa, can, AUTOLOAD, bless, use overload (operator overloading)
  • Exceptions: try/catch (typed and catch-all), finally, throw, die
  • Regex: =~, !~, s///, tr////y///, captures, named captures, /e modifier
  • I/O: say, print, printf, sprintf, core::open, core::close, diamond operator, core::slurp, core::spew
  • Modules: use (source inclusion), import_lib (native .so via dlopen)
  • BEGIN/END blocks, tie/untie/tied, BigInt/BigFloat, DateTime
  • Concurrency: async func/await and futures (async::spawn, all, race, timeout, cancel, ...), green tasks (Async::Loop / Async::Task), thread:: threads, mutexes and condition variables, channels; $_ is per thread and per green task
  • Numbers: integer overflow promotes exactly like the compiled backend (64-bit signed → 64-bit unsigned → floating point), e.g. 18446744073709551615 prints exactly
  • C interop: __C__ blocks (JIT-compiled), c::callback (libffi trampolines), import_lib
  • Introspection: core::exception_trace(), stacktrace_str() (returns the Strada frames), core::caller()
  • Namespaces: core::, math::, utf8:: — the VM exposes the full core::/math:: libc surface (~235 functions: process, users/groups, file I/O, sockets, extended math) through a generic runtime bridge
  • Regex: s///e evaluated replacements, tr/// with d/c/s/r flags, named captures, inline i/s/m/x flags, while ($s =~ /.../g) iteration, pattern interpolation; captures beyond $9 work and unmatched groups are undef
  • Context: reverse follows scalar/list context (my $r = reverse("ab", "cd") is "dcba")
  • Recursion limits: core::set_recursion_limit / core::get_recursion_limit

The bytecode VM runs the entire compiler test suite at parity: 108 pass, 0 fail (12 skips need shared-object compilation or compiled-format stack traces).

Limitations

Remaining differences from the compiled backend
  • DESTROY runs when the VM's garbage collector reclaims the object, not at the moment the last reference goes away
  • Raw pointers into variables (core::int_ptr and friends) are compiled-only
  • Functions declared in an extern "C" { ... } block cannot be called in the VM; a call raises a catchable error (extern "C" function NAME() is not available in the bytecode VM (compiled backend only))
  • Execution is slower than compiled native code

Native shared libraries loaded via import_lib still work — they are called through dlopen/dlsym regardless of execution mode.

Building

# Build the interpreter
make interpreter

# The interpreter binary
./interpreter/strada-interp --help

# Usage
Strada Interpreter v0.3 (Bytecode VM)
Usage:
  strada-interp                          Interactive REPL
  strada-interp [OPTIONS] <file.strada>  Execute file
  strada-interp -e 'code'                Execute code string

Options:
  -e CODE       Execute code (wraps in main() if needed)
  --vm          Use bytecode VM backend (default)
  -L PATH       Add library search path
  -h, --help    Show this help message

One-Liner Execution

Use -e to evaluate Strada code directly from the command line:

# Simple expression
strada-interp -e 'say("hello world")'

# Multiple -e flags are concatenated
strada-interp -e 'my $x = 6;' -e 'say($x * 7)'

# No func main() boilerplate needed
strada-interp -e 'my @nums = (1, 2, 3); foreach (@nums) { say($_); }'
